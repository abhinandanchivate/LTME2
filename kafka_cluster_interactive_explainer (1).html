CONCEPT 1 OF 6 — WHAT IS A KAFKA CLUSTER
A Kafka cluster is a group of servers working together to store and serve event streams. No single machine holds everything — the data is spread, replicated, and managed collectively so the system keeps running even when individual machines fail.

CONCEPT 2 OF 6 — BROKERS
A broker is just a server process. It receives messages from producers, writes them to disk as partition log files, and serves them to consumers. Each broker handles thousands of reads and writes per second by using sequential disk I/O — the secret behind Kafka's speed.
port9092 (plaintext default), 9093 (TLS)
storageSegment files on disk — each partition is a directory of .log files
why fastSequential writes + OS page cache + zero-copy transfer to consumers
stateless?No — each broker owns specific partition data
CONCEPT 3 OF 6 — TOPICS & PARTITIONS
A topic is a named category of events (like a database table, but append-only). Every topic is split into partitions — independent, ordered logs. Partitions are the unit of parallelism: more partitions means more consumers can read simultaneously. They are spread across brokers so no single broker holds an entire topic.
key ruleParallelism = min(partitions, consumers in group). Extra consumers sit idle.
orderingGuaranteed within a partition. Use message keys to route related events to the same partition.
CONCEPT 4 OF 6 — REPLICATION & ISR
Every partition is copied to multiple brokers. One copy is the leader — it handles all reads and writes. The others are followers. The ISR (In-Sync Replica set) is the subset of followers that are caught up with the leader. Only ISR members can become leader if the current leader fails.
acks=allProducer waits for ALL ISR replicas to confirm write. Safest, slowest.
acks=1Producer waits for leader only. Fast, but message lost if leader crashes before replication.
ISR thresholdreplica.lag.time.max.ms — follower evicted from ISR if it falls behind this long
min.insync.replicasMinimum ISR size before broker refuses writes. Prevents silent data loss.
CONCEPT 5 OF 6 — THE CONTROLLER
The Controller is a special broker role — one broker in the cluster is elected as Controller at any time. It is the brain of the cluster. It never touches data — it only manages metadata: who leads which partition, who is in the ISR, which brokers are alive. In modern Kafka (3.0+), this uses KRaft (Raft consensus built into Kafka itself), replacing the older ZooKeeper dependency.
ZooKeeper (old)External service. Kafka depended on it for leader election and cluster metadata. Required separate ops.
KRaft (new)Built-in Raft consensus. No external dependency. Faster startup, simpler deployment. Default since Kafka 3.3.
CONCEPT 6 OF 6 — FAILURE & RECOVERY
When a broker dies, the cluster self-heals automatically. The Controller detects the failure, picks a new leader for each affected partition from the ISR, and broadcasts the updated metadata. Producers and consumers transparently reroute — no manual intervention needed.
