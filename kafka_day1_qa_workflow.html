Q1What is a message queue and how does it differ from a database?▶

A message queue is a buffer that holds messages sent by producers until a consumer reads them. It decouples the sender from the receiver — the producer doesn't need to know who will consume the message or when.

A database stores data persistently for querying. A queue stores data transiently for delivery. Key differences: queues are optimized for throughput and delivery, not arbitrary reads; messages are typically deleted after consumption; and queues guarantee ordering within a channel whereas databases have no such guarantee by default.

Q2What is publish/subscribe messaging?▶

In pub/sub, producers publish messages to a named channel (topic) without knowing who will consume them. Multiple consumers can independently subscribe to that topic and each receive a copy of every message.

This contrasts with point-to-point queues where a message goes to exactly one consumer. Pub/sub enables fan-out — one payment event can simultaneously notify fraud detection, accounting, and notifications services.

Q3What does TCP guarantee that matters for messaging?▶

TCP guarantees ordered, reliable, byte-stream delivery between two endpoints. It handles retransmission if packets are lost and ensures the receiver gets bytes in the same order the sender sent them.

This matters for Kafka because producers and consumers communicate with brokers over TCP. The network layer is reliable, so Kafka's reliability model (ACKs, replication) builds on top of TCP without needing to solve packet-level reliability itself.

Q4What is eventual consistency in distributed systems?▶

Eventual consistency means that if you stop writing new data, all replicas will converge to the same value — eventually. There is no guarantee about how quickly that happens, or that a read immediately after a write will see the new value.

In Kafka's context, follower replicas are eventually consistent with the leader. When a leader fails, only replicas in the ISR (in-sync replica set) are eligible for promotion, which limits how stale a new leader can be.

module 1 — fundamentals
M1·1What exact problem does Kafka solve that a database or REST API can't?▶

A REST API is synchronous — the caller blocks until the callee responds. If the callee is slow or down, the caller fails. A database can store events, but every service would need to poll it continuously, creating massive read load and tight coupling.

Kafka solves the decoupled async delivery problem at scale. Producers write events without waiting for consumers. Consumers read at their own pace. The event log is retained so late-joining or replaying consumers don't miss anything. At high throughput (millions of events/sec), no REST API or database can match Kafka's sequential disk I/O model.

M1·2How is Kafka different from RabbitMQ or SQS?▶
RabbitMQ / SQSTraditional queue — message is deleted after a consumer acknowledges it. Each message goes to one consumer. No replay.
KafkaAppend-only log — messages are retained for a configurable duration. Multiple independent consumer groups each read the full log. Full replay is possible by resetting offsets.
key insightKafka is a distributed log, not a queue. The consumer "moving through a log" model is fundamentally different from "pulling from a queue."
M1·3Walk me through the payment event use case end-to-end▶

1. User clicks "Pay" → payment service produces an event {"payment_id":"p123","amount":500,"status":"initiated"} to the payments topic.

2. Three independent consumer groups read the same event: fraud-detection service (checks rules), ledger service (debits account), notifications service (sends SMS).

3. Each service processes at its own speed. If notifications is slow, it doesn't block fraud detection. If ledger crashes, it replays from its last committed offset.

4. A second event {"status":"completed"} is produced after bank confirmation. All consumers see both events in order within the partition.

module 2 — architecture
M2·1What exactly is a Kafka broker?▶

A broker is a server process that stores and serves event data. It receives messages from producers, writes them to disk in partition log files, and serves them to consumers on request.

A Kafka cluster is a group of brokers. Each broker holds some partitions as leader and some as follower replicas of other brokers' partitions. Brokers coordinate via ZooKeeper (legacy) or KRaft (modern). A single broker can handle hundreds of thousands of messages per second.

M2·2Why does Kafka partition topics — what are the trade-offs?▶

Partitions enable parallelism. A topic with 6 partitions across 3 brokers lets 6 consumer instances read simultaneously. Without partitions, a single topic would be a single-threaded bottleneck.

more partitionsHigher throughput, more parallelism, but more broker memory/file handles and slower leader election
fewer partitionsLower overhead, but capped parallelism — consumer group can never use more consumers than partitions
orderingOrdering is guaranteed only within a partition, not across partitions
M2·3What is an ISR and why does it matter?▶

ISR = In-Sync Replica set. It's the subset of replicas that are fully caught up with the partition leader (within a lag threshold defined by replica.lag.time.max.ms).

ISR matters for two reasons: (1) When acks=all, the producer only gets acknowledgement after all ISR replicas confirm the write — so ISR size directly affects write latency. (2) Only a replica in the ISR can be elected as the new leader when the current leader fails, preventing data loss from promoting a stale replica.

module 3 — producers and consumers
M3·1How do consumer offsets work, and who stores them?▶

An offset is an integer that marks the consumer's position in a partition log — the index of the last message successfully processed. Each consumer group maintains its own set of offsets, one per partition it reads.

Offsets are stored in the internal Kafka topic __consumer_offsets (since Kafka 0.9). The consumer commits offsets either automatically (every auto.commit.interval.ms) or manually after processing. On restart, the consumer resumes from its last committed offset rather than re-reading the whole log.

M3·2What is a consumer group and how does parallelism work?▶

A consumer group is a named set of consumer instances that jointly consume a topic. Kafka assigns each partition to exactly one consumer in the group at any time — no two consumers in the same group read the same partition simultaneously.

Parallelism rule: effective parallelism = min(num_partitions, num_consumers_in_group). With 6 partitions and 4 consumers, 4 consumers each get some partitions and throughput scales. With 4 partitions and 6 consumers, 2 consumers sit idle — adding more consumers beyond the partition count does nothing.

M3·3Explain at-most-once, at-least-once, and exactly-once delivery▶
at-most-onceCommit offset before processing. If the consumer crashes mid-process, the message is lost. Fast but lossy. Use when dropping events is acceptable.
at-least-onceCommit offset after processing. If the consumer crashes after processing but before committing, the message is re-delivered. Safe but may duplicate. Most common default.
exactly-onceRequires idempotent producers + transactional consumers. Kafka coordinates offset commit and output write atomically. Highest correctness, highest complexity and cost.
module 4 — reliability and ordering
M4·1What does acks=all mean and what does it cost in performance?▶

acks=all (equivalent to acks=-1) means the broker returns a success acknowledgement to the producer only after the partition leader has written the message AND all in-sync replicas have confirmed the write.

acks=0Fire and forget — fastest, no durability guarantee
acks=1Leader confirms — fast, but a message can be lost if the leader fails before replication
acks=allAll ISR replicas confirm — safest, but adds replication round-trip latency. Pair with min.insync.replicas=2 for best durability.
M4·2How do idempotent producers prevent duplicate messages?▶

Without idempotence: if a producer sends a message, the broker writes it, but the network drops the ACK — the producer retries and the broker writes a duplicate.

With enable.idempotence=true: every producer is assigned a PID (producer ID) and each message gets a monotonically increasing sequence number. The broker tracks the last sequence per PID per partition. If it receives a sequence number it has already seen, it silently deduplicates — no duplicate written, ACK sent back. This is transparent to application code.

M4·3How does key-based partitioning guarantee message ordering?▶

Kafka's default partitioner hashes the message key and maps it to a partition number: partition = hash(key) % num_partitions. All messages with the same key always land in the same partition.

Since Kafka guarantees ordering within a partition, all events for a given key are processed in the exact order they were produced. For payments: use user_id as the key so all events for a user land in one partition — debit always appears before refund for that user. Across different users, events may be interleaved, but that is fine since their ordering relative to each other is irrelevant.
