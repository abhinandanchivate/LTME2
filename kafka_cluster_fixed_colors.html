CONCEPT 1 OF 6 — WHAT IS A KAFKA CLUSTER
A Kafka cluster is a group of servers working together to store and serve event streams. Data is spread, replicated, and managed collectively so the system keeps running even when individual machines fail.

CONCEPT 2 OF 6 — BROKERS
A broker is a server process. It receives messages from producers, writes them to disk as partition log files, and serves them to consumers. Kafka's speed comes from sequential disk I/O and OS page cache — not RAM.
default port9092 (plaintext), 9093 (TLS)
storageSegment .log files on disk — one directory per partition
why fastSequential writes + OS page cache + zero-copy transfer to consumers
CONCEPT 3 OF 6 — TOPICS & PARTITIONS
A topic is a named category of events — append-only, like a log. Every topic is split into partitions spread across brokers. Partitions are the unit of parallelism: 3 partitions means up to 3 consumers can read simultaneously.
key ruleParallelism = min(partitions, consumers). Extra consumers sit idle.
key-based routinghash(key) % partitions → same key always lands in same partition → ordering per key
CONCEPT 4 OF 6 — REPLICATION & ISR
Every partition is copied to multiple brokers. One is the leader — it handles all reads and writes. The rest are followers. The ISR (In-Sync Replica set) is the subset of followers caught up with the leader. Only ISR members can be promoted to leader.
acks=allWait for all ISR replicas to confirm. Safest, adds latency.
acks=1Leader confirms only. Fast, but message lost if leader crashes before replication.
ISR evictionreplica.lag.time.max.ms — follower removed from ISR if it falls behind
min.insync.replicasMin ISR size before broker refuses writes. Prevents silent data loss.
CONCEPT 5 OF 6 — THE CONTROLLER
One broker in the cluster is elected as Controller. It's the brain — it never touches data, only metadata: who leads which partition, who is in the ISR, which brokers are alive. Modern Kafka (3.3+) uses KRaft (built-in Raft consensus), replacing the older ZooKeeper dependency.
ZooKeeper (old)External service. Separate ops burden. Required for older Kafka clusters.
KRaft (new)Built-in Raft consensus. No external dependency. Default since Kafka 3.3.
CONCEPT 6 OF 6 — FAILURE & RECOVERY
When a broker dies the cluster self-heals. The Controller detects the failure, picks a new leader for each affected partition from the ISR, and broadcasts updated metadata. Producers and consumers reroute automatically — no manual intervention needed.
